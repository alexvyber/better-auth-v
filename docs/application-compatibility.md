# Application compatibility gate

`tests/contracts/application-schema-contract.test.ts` runs the official Better Auth client
through a loopback HTTP server into native V authentication. The Node server only
translates request/response bytes and headers. Authentication, session renewal,
authorization, transactions and persistence execute in V.

## Brand Map

The checked-in PostgreSQL fixture contains all ten auth tables from Brand Map's
`20261102120000_catalog_baseline` migration: users, accounts, sessions,
verifications, organizations, organization roles, members, invitations, two-factor
records and JWKS. The 72 extracted statements preserve column types, UUIDv7
defaults, enum values, indexes, checks and auth-side foreign keys. A minimal
`file(id)` table satisfies the references to the separate file service. Tests
require PostgreSQL 18 and create a fresh schema in an ephemeral cluster.

Source paths/checksums and the extraction adaptations are recorded beside the
snapshot in `tests/fixtures/brand-map-schema.json`. Field mappings, permission
statements and all configured organization roles are snapshotted from the actual
application source in `brand-map-config.json`. Update these fixtures explicitly:

```sh
node scripts/snapshot-brand-map-schema.mjs /path/to/bm/server
```

The fixture configures bearer, JWT, organizations with dynamic access control,
anonymous users, email OTP, one-time tokens, two-factor and admin together. It uses
the application's `/auth` path, table/column mappings, protected profile/review
fields, 30-day sessions and one-day renewal policy. Username validation uses a
Standard Schema equivalent of the application's Valibot regex. Email delivery and
domain effects are test callbacks; application services are not imported.

Tests seed users, credential hashes generated by the upstream implementation, and
existing sessions before V connects. Cookie signing also uses the upstream
implementation. Native migrations are disabled. Coverage includes:

- Existing credentials, cookies, bearer tokens and mapped profile/date/JSON data.
- Session renewal, independent connections, restart and cross-instance revocation.
- JWT key creation in the existing JWKS table, without schema changes.
- Protected-field rejection, update effects and preservation of domain-owned data.
- Organization creation, active sessions, member joins, externally provisioned
  role grants, invitations and the application's `accessControl` versus upstream
  `ac` permission distinction.
- Hashed email OTP login and single-use one-time-token verification.

An information-schema/constraint/index fingerprint before and after the session
test verifies that those native operations do not modify the application schema.

## Nabu

The MongoDB fixture installs Nabu's email, token, account-key, identifier,
database-rate-limit and session-TTL indexes before V connects. It inserts existing
users, credential accounts and sessions directly as ObjectId/BSON-date documents,
then disables native migrations. The password-mode configuration uses Nabu's
signup restrictions, minimum password length, 30-day sessions, one-day renewal
and database rate limiter.

The official client verifies upstream cookies/credentials, renewal, independent
clients, restart, revocation, disabled public signup and preservation of
application-owned document fields. The separate `nabu-oidc-contract.test.ts` matrix
covers signed OIDC, Basic client authentication, PKCE, provisioning policy,
linking, rollback and proof replay. Its MongoDB provisioning case also installs
application indexes and directly seeds an unverified user before native
initialization, with native migrations disabled. The verified IdP callback updates
that existing row and retains its ObjectId and application-owned fields.

## Limits

This is an auth-schema and configuration compatibility gate, not a deployment of
either complete application. No application database or environment is accessed.
Domain services, the real identity provider, Redis integration with these exact
configurations, cross-service foreign-key behavior and the full application test
suites remain outside this gate. Two-factor/admin/anonymous plugin combinations
still need additional application-level scenarios, beyond their existing native
and imported upstream suites. Generic PostgreSQL/MongoDB adapter query/join and
transaction failure/retry conformance also remain incomplete.
